# 烟火小食单 V1 研发执行批次（Task4）

## 1. 目标与输入

- 目标：将 `V1` 核心域拆分为可直接用于排期会的研发执行批次，确保依赖有序、单批次可交付、验收可独立。
- 输入依据：
  - `docs/superpowers/plans/2026-04-23-烟火小食单-研发拆分矩阵.md`
  - `docs/superpowers/specs/2026-04-23-烟火小食单-研发版脑图结构.md`

## 2. 批次失败条件（统一判定）

任一批次命中以下任一条即判定“分批失败”，需重排：

1. 依赖未满足：批次所需上游模块/数据对象/API 未先行可用。
2. 单批次过大：同一批次内跨域过多，无法在一个迭代内完成联调与回归。
3. 验收不可独立：批次验收依赖未交付能力，无法形成可单独通过的检查闭环。

## 3. 初版分批失败点（示例）

> 初版（失败）思路：按业务域并行推进 `AUTH/DISH/INGR/MENU/COOK/REVIEW/PREP`，希望一次性完成。

### 3.1 失败点清单

- 失败点 A（依赖未满足）：
  - 将 `COOK` 与 `PREP/REVIEW` 放在首批，但 `COOK` 依赖 `MENU` 模板与 `DISH-INGR` 关联数据，基础数据链路未准备完成。
- 失败点 B（单批次过大）：
  - 同批次覆盖七大域，接口与对象数量过多，回归面过宽，超出单迭代容量。
- 失败点 C（验收不可独立）：
  - `REVIEW` 评分能力验收依赖“已完成会话”，若 `COOK` 会话闭环未稳定，`REVIEW` 无法独立验收。

### 3.2 初版结论

- 初版不满足批次设计要求，必须按“基础能力 -> 组合能力 -> 业务闭环”重排。

## 4. 修复后：依赖有序批次（排期可用）

> 排序原则：先交付基础主数据与权限底座，再交付模板与会话主链路，最后交付备菜与评价扩展能力。

### Batch 1：基础底座与主数据（建议迭代 W1）

- 目标模块：
  - `auth-account`（P-AUTH-001）
  - `auth-role`（P-AUTH-002）
  - `auth-permission`（P-AUTH-003）
  - `auth-scope`（P-AUTH-004）
  - `dish-core`（P-DISH-001）
  - `dish-cuisine`（P-DISH-002）
  - `dish-category`（P-DISH-003）
  - `dish-tag`（P-DISH-004）
  - `ingredient-core`（P-INGR-001）
  - `ingredient-category`（P-INGR-002）
  - `ingredient-nutrition`（P-INGR-003）
- 前置依赖：
  - 无业务前置；仅需统一 API 响应与异常处理框架可用。
- 交付物：
  - 账号、角色、权限、端范围管理 API 可联调。
  - 菜品主数据与食材主数据 CRUD API 可联调。
  - 对应 `Req/Entity/VO`、参数校验、统一错误响应落地。
- 验收检查点：
  - 权限分配后访问控制即时生效，越权访问被拒绝。
  - 菜品/食材新增、编辑、查询通过；唯一性冲突返回统一业务错误。
  - 七层链路中本批次能力均具备“API -> 数据对象 -> 验收”闭环。

### Batch 2：主链路组装（建议迭代 W2）

- 目标模块：
  - `ingredient-link`（P-INGR-004）
  - `dish-media`（P-DISH-005）
  - `menu-template`（P-MENU-001）
  - `menu-type`（P-MENU-002）
  - `menu-scene-crowd`（P-MENU-003）
  - `menu-ingredient-summary`（P-MENU-004）
  - `cooking-session`（P-COOK-001）
  - `cooking-timeline`（P-COOK-002）
  - `cooking-history`（P-COOK-003）
  - `cooking-retrospective`（P-COOK-004）
- 前置依赖：
  - 依赖 Batch 1 的菜品、食材、分类与权限底座。
- 交付物：
  - 菜品-食材关联维护与菜品图文步骤维护能力可用。
  - 菜单模板、类型、场景人群匹配及食材汇总能力可用。
  - 烹饪会话创建、过程事件、历史与复盘闭环 API 可联调。
- 验收检查点：
  - 菜品食材关联后，模板食材汇总接口可正确聚合数量。
  - 会话创建满足“菜单/模板二选一 + 开始时间必填”规则。
  - 会话时间线、历史查询、复盘提交形成可回看闭环。

### Batch 3：备菜与评价闭环（建议迭代 W3）

- 目标模块：
  - `prep-list`（P-PREP-001, P-PREP-002）
  - `prep-status`（P-PREP-003）
  - `prep-shortage`（P-PREP-004）
  - `review-score`（P-REVIEW-001, P-REVIEW-002）
  - `review-intent`（P-REVIEW-003）
  - `review-note`（P-REVIEW-004）
- 前置依赖：
  - 依赖 Batch 2 的会话、模板食材汇总、菜品食材关联。
- 交付物：
  - 备菜清单生成、明细查询、准备进度、缺货确认完整能力上线。
  - 口味/难度评分、复做意愿、点评备注 API 完成联调。
  - 基于会话的“备菜 -> 烹饪 -> 评价”端到端业务闭环可演示。
- 验收检查点：
  - 一键生成备菜清单后，明细与模板食材汇总一致。
  - 备菜状态仅允许 `TODO -> READY` 合法流转，进度实时可查询。
  - 评分范围、会话状态、备注长度等约束生效，错误响应统一。

## 5. 排期会使用建议（可直接执行）

- 会议输入：按 Batch 1/2/3 逐批评估人天、风险、联调窗口。

- 联调节奏：每批次末保留固定联调与回归窗口，避免跨批次返工扩大。
