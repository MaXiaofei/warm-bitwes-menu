# 烟火小食单研发版脑图结构（Task3）

## 1. 目标与范围

- 目标：基于产品版信息架构与研发拆分矩阵，落地“可直接改图”的研发版脑图骨架。
- 范围：仅覆盖 `V1` 核心域：`AUTH`、`DISH`、`INGR`、`MENU`、`COOK`、`REVIEW`、`PREP`。
- 追踪要求：所有研发节点必须可追溯到产品节点 ID（`P-<DOMAIN>-NNN`）。

## 2. 研发版层级规则（统一五层）

研发版脑图统一采用以下五层结构，不增不减：

1. 模块（Module）
2. 能力（Capability）
3. API（方法 + 路径）
4. 数据对象（DTO/Entity/VO）
5. 验收（可验证标准）

### 2.1 命名与落图规则

- 模块层命名：`<domain>-<module>`，例如 `auth-account`、`dish-core`。
- 能力层命名：使用业务动词短语，例如“账号管理”“菜品维护”“备菜清单生成”。
- API 层命名：固定写法 `METHOD /path`，同能力下按“查 -> 增 -> 改”顺序。
- 数据对象层命名：按接口链路最小闭环列出 `Req/Entity/VO`。
- 验收层命名：使用“当...时...则...”可测试语句，避免抽象描述。

## 3. V1 核心域五层链路示例（全域覆盖）

> 说明：每个核心域至少给出 1 条“模块 -> 能力 -> API -> 数据对象 -> 验收”完整链路示例。

### 3.1 AUTH 域

- 模块：`auth-account`
  - 能力：账号管理（`P-AUTH-001`）
    - API：`POST /api/admin/users`
      - 数据对象：`UserCreateReq`、`User`、`UserVO`
        - 验收：当提交唯一账号且参数合法时创建成功；当账号重复时返回统一错误响应（非 0 业务码）。

### 3.2 DISH 域

- 模块：`dish-core`
  - 能力：菜品维护（`P-DISH-001`）
    - API：`POST /api/dishes`
      - 数据对象：`DishCreateReq`、`Dish`、`DishDetailVO`
        - 验收：当菜名非空且烹饪时长大于 0 时保存成功；当参数非法时返回统一失败响应。

### 3.3 INGR 域

- 模块：`ingredient-core`
  - 能力：食材维护（`P-INGR-001`）
    - API：`POST /api/ingredients`
      - 数据对象：`IngredientCreateReq`、`Ingredient`、`IngredientVO`
        - 验收：当食材名称唯一且单位存在时创建成功；当名称冲突时返回统一错误响应。

### 3.4 MENU 域

- 模块：`menu-template`
  - 能力：菜单模板维护（`P-MENU-001`）
    - API：`POST /api/menu-templates`
      - 数据对象：`MenuTemplateCreateReq`、`MenuTemplate`、`MenuTemplateVO`
        - 验收：当模板至少包含一道菜且模板名唯一时保存成功；保存后详情可完整回显。

### 3.5 COOK 域

- 模块：`cooking-session`
  - 能力：烹饪记录创建（`P-COOK-001`）
    - API：`POST /api/cook-sessions`
      - 数据对象：`CookSessionCreateReq`、`CookSession`、`CookSessionVO`
        - 验收：当菜单/模板二选一且开始时间存在时创建成功；创建后可通过会话 ID 查询到记录。

### 3.6 REVIEW 域

- 模块：`review-score`
  - 能力：口味评分（`P-REVIEW-001`）
    - API：`POST /api/cook-sessions/{id}/reviews/taste`
      - 数据对象：`TasteReviewReq`、`Review`、`ReviewVO`
        - 验收：当评分范围在 1-5 时提交成功；超范围或会话不存在时返回统一失败响应。

### 3.7 PREP 域

- 模块：`prep-list`
  - 能力：备菜清单生成（`P-PREP-001`）
    - API：`POST /api/cook-sessions/{id}/prep-list/generate`
      - 数据对象：`PrepListGenerateReq`、`PrepItem`、`PrepListVO`
        - 验收：当会话存在且菜品食材关联完整时生成成功；生成后清单可查询并与模板食材一致。

## 4. 当前脑图差距检查（失败）-> 改图动作 -> 复核通过标准

### 4.1 当前脑图差距检查（失败）

- 失败项 1：当前结构仍以产品视角节点为主，未统一落实“五层研发结构”。
- 失败项 2：部分域仅到“功能/API”层，缺失“数据对象/验收”层。
- 失败项 3：`AUTH/DISH/INGR/MENU/COOK/REVIEW/PREP` 七域未全部形成完整五层链路。
- 失败项 4：产品 ID 与研发节点映射关系在脑图中不可见，追踪性不足。

### 4.2 改图动作

- 动作 1：在研发版脑图中统一重排为“模块 -> 能力 -> API -> 数据对象 -> 验收”五层模板。
- 动作 2：按七大核心域逐域补齐至少 1 条完整五层链路，并在能力层追加产品 ID（如 `P-DISH-001`）。
- 动作 3：将验收层统一改为可验证语句（成功条件 + 失败条件）。
- 动作 4：抽查每域链路是否可从模块直达验收，保证无断层节点。

### 4.3 复核通过标准

- 标准 1：七大核心域全部出现，且每域至少存在 1 条完整五层链路。
- 标准 2：任意抽取一个能力节点，均可向下看到 API、数据对象、验收三层完整信息。
- 标准 3：每条能力链路均标注对应产品 ID，且可在产品节点清单中定位。
- 标准 4：验收描述可直接转为联调检查项，不含“完善后补充”等模糊表述。

## 5. 把此结构映射回 xmind 的操作步骤（手工改图步骤）

1. 打开现有产品版脑图，另存为“研发版”副本（仅改结构，不改产品语义）。
2. 在顶层新增主节点：`研发版（V1 核心域）`，其下创建七个二级域节点：`AUTH`、`DISH`、`INGR`、`MENU`、`COOK`、`REVIEW`、`PREP`。
3. 在每个域下先创建“模块”层节点，再挂“能力”层；能力节点名称后追加产品 ID（例如：`菜品维护（P-DISH-001）`）。
4. 在每个能力节点下依次新增三层子节点：`API`、`数据对象`、`验收`。
5. API 层中逐条录入 `METHOD /path`；数据对象层录入 `Req/Entity/VO`；验收层录入“成功条件 + 失败条件”。
6. 对七个域逐一做完整性检查：是否至少一条五层链路、是否含产品 ID、是否含可验证验收句。
7. 完成后执行一次全图巡检：同名能力去重、链路层级一致、ID 可回溯到产品节点清单与研发拆分矩阵。
