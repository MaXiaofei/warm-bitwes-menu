# 烟火小食单信息架构设计（产品版优先）

## 1. 背景与目标

本设计用于完善 `烟火小食单` 脑图结构，先产出可用于需求评审的产品版，再在同一语义基础上拆分研发版。  
目标是降低重复节点、明确跨端共享能力边界，并保证后续可平滑映射到模块与接口实现。

## 2. 已确认决策

- 优先任务：信息架构重组。
- 一级组织视角：按角色端组织（管理后台 / 小程序端）。
- 重复功能处理：提取 `共享能力` 分组，端内仅保留入口与端内动作。
- 共享粒度：除端 UI 之外，业务能力尽量共享（高度共享）。
- 交付策略：先产品版，后研发版（两份脑图/视图）。

## 3. 可选方案对比与推荐

### 方案 1：双端主树 + 共享能力中台（推荐）

- 一级：`烟火管理后台`、`小食单（小程序）`、`共享能力`。
- 两端仅保留端内流程与入口，业务规则与主数据沉入 `共享能力`。
- 优点：复用关系清晰，后续接口与模块映射成本最低。

### 方案 2：双端主树 + 共享能力标签化

- 仍按双端展开，不单独拆共享树，仅用标签标记共享。
- 优点：改动小，阅读习惯延续。
- 风险：重复节点长期维护成本高，易出现定义漂移。

### 方案 3：共享能力主树 + 双端消费视图

- 先按共享能力建树，端能力作为消费视图挂接。
- 优点：研发落地最强。
- 风险：产品评审可读性偏弱。

推荐采用方案 1。

## 4. 产品版脑图目标结构

### 4.1 一级结构

- `烟火管理后台`
- `小食单（小程序）`
- `共享能力`
- `版本规划`

### 4.2 管理后台（端能力）

- 账号与权限：用户、角色、权限配置、端权限范围。
- 内容维护：菜品维护、食材维护、菜单模板维护、标签分类维护。
- 运营配置：口味、场景、人群、菜系、基础字典与开关。
- 记录与数据：烹饪记录、点评记录、菜品使用情况、基础统计。

### 4.3 小程序端（用户旅程）

- 点菜：按场景/口味/人群选菜，按模板选菜，自定义搭配。
- 备菜：生成清单、所需食材、准备状态、缺货提示。
- 做饭：查看做法步骤、多菜协同、过程记录。
- 点评：口味、难度、复做意愿、备注。
- 复盘：历史记录回看、常做菜沉淀、下次菜单建议。
- 我的：偏好、历史、收藏、常用菜单。

### 4.4 共享能力（跨端业务资产）

- 账号与身份：登录、鉴权、能力边界。
- 菜品中心：菜品、菜系、分类、标签、图文信息。
- 食材中心：食材、营养信息、分类、菜品关联。
- 菜单中心：模板、类型、场景、人群、所需食材。
- 烹饪与复盘中心：烹饪记录、评分记录、复盘结论、常用菜单沉淀。
- 标签与字典体系：场景、口味、人群、分类、标签。
- 媒体与附件：封面图、步骤图及素材。
- 数据沉淀：热度、频次、评分分布、偏好趋势。

### 4.5 版本规划

- `V1 必做`：菜品中心、食材中心、模板、点菜、备菜、烹饪记录、点评复盘、后台基础维护。
- `V1 可选`：收藏、常用菜单、基础推荐、简单报表。
- `V2 演进`：个性化推荐、细粒度营养分析、智能搭配、任务提醒、高级报表。

## 5. 边界与冲突处理规则

- 管理后台只承担配置、维护、审核、查看，不承载用户主流程。
- 小程序只承担用户交互与体验，不承载业务规则定义。
- 共享能力是业务真相唯一来源（Single Source of Truth）。
- 端内节点仅描述入口动作，不复制共享规则细节。
- 冲突优先级：`V1 必做` > `V1 可选` > `V2`。

## 6. 产品版到研发版拆分规则

每个产品功能节点拆分为以下研发子节点：

- 模块（module）
- 接口（api）
- 数据对象（data model）
- 校验与异常（validation/error）
- 验收标准（acceptance）

并为产品节点分配唯一标识（例如 `P-REVIEW-001`），研发版必须引用该标识以保证追踪。

### 6.1 产品节点 ID 规则

- 统一格式：`P-<DOMAIN>-NNN`。
  - `P` 固定表示产品节点（Product）。
  - `<DOMAIN>` 表示能力域，采用全大写英文缩写（如：`AUTH`、`DISH`、`INGR`、`MENU`、`COOK`、`REVIEW`、`PREP`、`PLAN`）。
  - `NNN` 为三位流水号（`001` 起），同一 `<DOMAIN>` 内连续编号。
- 唯一性要求：同一版本信息架构内，任意两个产品节点不得复用同一个 ID；禁止一号多义、禁止同义多号。
- 覆盖要求：`V1 必做` 节点必须实现 ID 全覆盖，且在产品版与研发版中保持同一 ID 引用。
- 变更要求：节点名称可演进，但若节点语义不变则 ID 不变；如语义拆分或合并，需在节点清单中记录映射关系后再调整 ID。

## 7. 脑图改造执行顺序（一次性改图清单）

1. 新增一级节点：`共享能力`、`版本规划`。
2. 将 `菜品管理`、`食材管理`、`菜单` 从后台私有分支迁移到 `共享能力`。
3. 将 `烹饪记录` 合并为共享能力唯一节点；后台/小程序保留入口节点。
4. 将小程序 `点评`、`备菜清单` 上升为主流程节点（与点菜、做饭、复盘并列）。
5. 将 `菜系/标签/分类/场景/人群` 统一归入 `标签与字典体系`。
6. 在 `版本规划` 中给主要功能打上 `V1 必做/V1 可选/V2` 标签。

## 8. 验收标准（产品版）

- 从任一功能节点可判断所属端与共享归属。
- 不存在同一业务规则在多端重复定义。
- 所有核心功能都有版本归属标签。
- 产品版节点可被研发版按规则拆分，不发生语义断层。
