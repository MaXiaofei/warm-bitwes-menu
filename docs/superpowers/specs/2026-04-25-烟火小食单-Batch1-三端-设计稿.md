# 烟火小食单（Batch 1）三端（后端 + 管理后台 + 小程序）设计稿

> 范围选择：**仅 Batch 1**（AUTH + DISH + INGR）。  
> 三端技术路线选择：**方案 3**（管理后台：Vue3；小程序：uni-app）。  
> 管理后台信息架构：**A 版（业务优先：主数据在前）**。  
> AUTH 选择：**A1（真实鉴权 + 越权拒绝）**。  

## 1. 目标（Goal）

- 在现有 `menu` 后端基础上，补齐并稳定 Batch 1 的最小可交付闭环，使其支持：
  - 管理后台：主数据（菜品/食材）管理 + 账号/角色/权限管理（含端权限范围）可联调、可验收
  - 小程序：登录态可建立；提供“发现/我的”骨架与只读浏览入口（菜品/食材列表与详情，可分阶段启用）
- 所有接口遵循仓库统一响应：`code` / `message` / `data`（成功 `code=0`）。

## 2. 范围与非范围（Scope / Non-goals）

### 2.1 In Scope（Batch 1）

对应产品节点（基线清单）：
- AUTH：`P-AUTH-001` 账号管理、`P-AUTH-002` 角色管理、`P-AUTH-003` 权限配置、`P-AUTH-004` 端权限范围
- DISH：`P-DISH-001` 菜品维护（及其在 Batch 1 里的主数据面）
- INGR：`P-INGR-001` 食材维护（及其在 Batch 1 里的主数据面）

### 2.2 Out of Scope（本设计稿明确不做）

- Batch 2/3：菜单模板、烹饪会话、备菜清单、点评闭环等能力（后端即使已有部分代码，也不以本批次验收为准）
- 复杂小程序体验（本批次以“可登录 + 可占位 + 可只读浏览”为主）

## 3. 现状与差距（Current State / Gaps）

### 3.1 后端现状（`menu`）

- 已存在接口族（示例）：
  - `GET/POST/PUT/DELETE /api/dishes`（菜品）
  - `GET/POST/PUT/DELETE /api/ingredients`（食材）
  - `POST /api/auth/login`（当前为最小可联调实现：返回随机 token）
- 差距（与 Batch 1 的 A1 验收一致性）：
  - 登录 token 目前不具备“真实鉴权/权限校验/越权拒绝”的能力，需要在 Batch 1 内补齐
  - 缺少明确的“管理端账号/角色/权限/端范围”API 族（需要按模块落地，并与统一响应/全局异常处理对齐）

### 3.2 管理后台 / 小程序现状

- `menu-admin`、`menu-mini` 当前为空工程（仅 `.cursor`），需从零搭建。

## 4. 三端整体架构（High-level Architecture）

### 4.1 系统组成

- `menu`（后端）：提供 Batch 1 API
- `menu-admin`（管理后台，Vue3）：面向运营/管理人员做主数据与权限配置
- `menu-mini`（小程序，uni-app）：面向普通用户（或内部测试用户）做登录态与只读浏览

### 4.2 鉴权与权限（A1 约束）

- 认证（Authentication）：登录成功后获得 `accessToken`（后续可扩展 refreshToken，但本批次至少 accessToken 可用）
- 授权（Authorization）：
  - **后端以 API 权限点为主**（你已确认）
  - 前端（admin/mini）以“路由/按钮”映射到 API 权限点做展示控制，但最终以**后端拒绝越权请求**为准
- 端权限范围（Scope）：同一账号/角色可配置其是否允许访问：
  - 管理后台（admin）
  - 小程序（mini）

## 5. 管理后台信息架构与页面设计（A 版 + 暖色调）

### 5.1 导航结构（A 版：业务优先）

- **主数据**
  - 菜品管理
  - 食材管理
  - 菜系 / 分类 / 标签（Batch 1 可先做最小可用，或作为二级折叠）
- **权限**
  - 账号管理（`P-AUTH-001`）
  - 角色管理（`P-AUTH-002`）
  - 权限配置（`P-AUTH-003`）
  - 端权限范围（`P-AUTH-004`）

### 5.2 UI 风格（暖色调约束）

- 主色倾向暖色（橙/琥珀系），但表格/表单保持高可读性
- 在不牺牲信息密度的前提下，页面顶部区域可加入轻量暖色背景块用于“筛选区/关键操作区”分层

### 5.3 关键页面（Batch 1 必做）

#### 5.3.1 账号管理（列表 + 抽屉表单）

- 列表字段（展示）：
  - 账号、昵称、手机号、邮箱、状态、角色（多选显示）、操作
- 抽屉表单字段（新增/编辑）：
  - **账号（唯一）**
  - 昵称
  - **手机号（可选）**
  - **邮箱（可选）**
  - 密码（新增必填；编辑可选重置）
  - 状态（启用/禁用）
  - 角色（多选）

#### 5.3.2 角色管理（列表 + 授权入口）

- 列表字段：角色名、备注、操作（编辑、配置权限、配置端范围）
- 角色删除策略：若已有账号绑定则禁止删除（或需要先解绑）

#### 5.3.3 权限配置（独立页）

- 顶部：选择角色（下拉） + 保存按钮
- 主体：权限点列表（按模块分组） + 已选权限集合（可搜索/批量移除）
- 权限点来源：后端提供“权限点枚举/列表”API（Batch 1 内必须稳定）

#### 5.3.4 端权限范围（独立页或角色页子面板）

- 角色维度配置：
  - 允许访问管理后台（admin）
  - 允许访问小程序（mini）
- 保存后立即生效：对应端登录/刷新时若无权限则拒绝进入

#### 5.3.5 菜品管理（列表 + 抽屉表单）

- 列表字段：菜名、时长（分钟）、难度、状态、操作（编辑、上下架、删除）
- 表单字段（Batch 1）：
  - 菜名（必填、唯一策略需明确）
  - 封面图 URL（可选）
  - 步骤（可选，文本或富文本后续再定）
  - 备注（可选）
  - 时长（>0）
  - 难度（范围约束）
  - 状态（上架/下架）

#### 5.3.6 食材管理（列表 + 抽屉表单）

- 列表字段：食材名、单位、热量、GI、操作
- 表单字段（Batch 1）：
  - 食材名（必填、唯一策略需明确）
  - 单位（必填）
  - 热量（kcal/100g，可选）
  - GI（可选）
  - 可选扩展：蛋白质/脂肪/碳水（对齐 DDL 清单建议项）

## 6. 小程序信息架构（uni-app，Batch 1）

### 6.1 页面结构

- 底部 Tab：
  - 发现：入口卡片（菜品列表 / 食材列表）
  - 我的：登录/退出、基础账号信息（占位）

### 6.2 登录态

- 未登录：
  - “我的”页显示登录按钮
  - “发现”页可展示内容占位或只读列表（由你后续决定是否必须登录）
- 已登录：
  - “我的”页展示账号信息（昵称/手机号/邮箱可选）+ 退出
  - 访问后端接口时带上 token

## 7. API 设计原则（与研发版五层结构一致）

遵循研发版脑图的五层结构：**模块 -> 能力 -> API -> 数据对象 -> 验收**。

本批次特别强调：
- API 命名与路径：按模块聚合（管理后台建议走 `/api/admin/...` 或至少逻辑分组清晰）
- DTO/Entity/VO：按“最小闭环链路”列齐
- 验收语句必须可验证（包含成功条件 + 失败条件）

## 8. 验收标准（Batch 1）

### 8.1 AUTH（A1）

- 当账号密码正确时可登录成功并获得 token；当密码错误/账号禁用时返回统一失败响应（非 0 业务码）
- 当访问受保护 API 且无权限时，后端必须拒绝（统一失败响应）
- 端权限范围生效：无 admin 范围不得进入管理后台；无 mini 范围不得在小程序登录后访问受保护能力

### 8.2 主数据

- 菜品/食材 CRUD 正常；参数非法与唯一性冲突返回统一失败响应
