# 三端开发进度与版本规划（设计说明）

> 状态：已由 brainstorming 收敛为 **方案 A**：对外里程碑严格对齐 `Batch1 → Batch2 → Batch3`（见 `docs/superpowers/plans/2026-04-23-烟火小食单-V1-研发执行批次.md`）。  
> 协作策略：采用 **后端先行、前端跟批**（同一 Batch 内完成对本批 API 的三端最小联调闭环；不以「三端代码同一天齐」为硬门禁）。

## 1. 版本语义

| 里程碑 | 含义 |
|--------|------|
| **V1.0-Batch1** | 完成 Batch1 文档中的目标模块与验收检查点所要求的 **最小可演示闭环**：后端 API 与数据为准；管理端完成主数据与权限配置；小程序完成只读浏览与端范围/鉴权行为。 |
| **V1.0-Batch2** | Batch1 已冻结后，交付 Batch2（模板、会话链路等）及三端最小联调面。 |
| **V1.0-Batch3** | 备菜与评价闭环及端到端演示。 |

对外若统一称 **V1.0**，可将 Batch1/2/3 作为 **内部里程碑编号**，与产品沟通时说明对应能力范围即可。

## 2. 当前进度基线（事实）

- **`menu`**：`dev` / `main` 已对齐，Batch1 相关后端能力已合入主线；若需「正式关门」仍建议对照 `docs/superpowers/plans/2026-04-25-烟火小食单-Batch1-后端实施计划.md` 内 checkbox 做一次性勾选盘点。  
- **`menu-admin`** / **`menu-mini`**：Batch1 工程与文档已进 **`main`**（具体以各仓库 `main` 为准）；历史 `.worktrees/batch1-*` 仅作遗留副本时可忽略或清理。  
- **下一阶段**：在 Batch1 验收无异议前提下，按 **`docs/superpowers/plans/2026-05-09-V1-Batch2-三端实施计划.md`** 推进 **V1.0-Batch2**。

## 3. Batch1 收口硬条件（进入 Batch2 前）

1. **分支与目录收口**：将 `feat/batch1-admin`、`feat/batch1-mini` 合入各仓库 **可协作的主线**（默认 `main`；若团队改用 `develop`，全文替换目标分支名）。合入后删除或归档孤立 worktree，避免「代码在旁路目录」的认知风险。  
2. **联调清单**：以后端为真源，结合 `docs/superpowers/specs/2026-04-25-鉴权联调说明.md` 与两份 Batch1 前端实施计划，固化 **最少页面 + API 列表** 作为 Batch1 验收子表。  
3. **冻结规则**：沿用 V1 批次文档 —— **Batch1 检查点未过，不在默认分支上合并 Batch2 行为**（允许在独立分支预研，但不得污染主线发布节奏）。

## 4. Batch2 / Batch3

范围、依赖与验收检查点 **以** `docs/superpowers/plans/2026-04-23-烟火小食单-V1-研发执行批次.md` **为准**，本设计不重复扩写，避免与权威文档分叉。

## 5. 风险与最小测试

- **最大风险**：三端物理分仓 + worktree，导致误判「Batch1 已完成」。  
- **最小测试**：Batch1 关门时至少具备：后端关键接口自动化测试可绿；管理端「登录 → 主数据 CRUD」冒烟；小程序「登录 → 只读列表/详情」冒烟。
